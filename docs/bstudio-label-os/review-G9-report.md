### 2. Findings
**Medium — Org export omitted most of the data added after LABEL-39** (`src/lib/labelos/org-export.ts`). `EXPORT_TABLES` lacked `parties`, `track_collaborators` (credits), `split_sheets`, `split_lines`, `approvals`, `artist_direction`, `artist_references`, `connection_projects` and `org_connections`. An owner's "export of the org" therefore left out the whole rights/legal record and sharing config. Existing test only checked list shape. **Fixed** (commits 1a731ff, 1257c74): tables added, `either` source for `org_connections` (label or artist side), and a drift test that scans migrations for every table with an `org_id` and fails unless exported or listed with a reason (notifications, `org_digest_*` are the only reasoned exclusions). Test failed before the fix.

**Medium — Restore could undo a purge already in progress** (`org-lifecycle-store.ts#restoreOrg`). The cron deletes objects (masters) first, row second. Restore checked grace only against the route's clock; a request straddling day 30 passes `canRestore`, the CAS on `deleted_at` still matches, org comes back with its files gone. **Fixed** (5ab2143): the same UPDATE also requires `deleted_at > purgeCutoff(now)`. Test failed first.

**Low — Purge loop has no time budget** (`cron/purge-deleted-orgs`). Orgs stuck on object deletion are retried oldest-first every day (25 considered, sequential, `maxDuration` 300, each up to 50×1000 keys per bucket), so a few stuck old orgs can starve newer ones and the function can be killed mid-run (safe: idempotent). Proposed: a 45–60 s budget like the weekly digest.

**Low — Public release routes are unthrottled except audio.** `/api/store/releases/[id]` and `/cover` have no limiter; query-string cache busting bypasses the CDN and each hit costs ~6–8 queries (+ a private-bucket stream for the cover). Proposed: limiter keyed on lower-cased id.

**Medium (decision) — `full` playback = anonymous access to the raw master, throttled only per instance.** `audio/[itemId]` in `full` mode streams `tracks.audio_url` (the uploaded master, possibly WAV) with Range forwarded. A single `Range: bytes=0-` is the whole file in one request, so "90 requests/min/IP/release" bounds nothing; the limiter is per-serverless-instance memory (`rateLimit`), keyed by IP+release. Cost/abuse amplification and a free lossless download. `rateLimitDurable` exists (mig 074).

**Low — Audit-class verbs without an atomic function.** `org.deletion_scheduled`, `org.restored`, `org.exported`, `release.store_listed/unlisted/delivered`, `digest.channel_*` write the change then the event with a best-effort put-back. Builders documented it; the repo rule asks for one SECURITY DEFINER function (needs a migration → not done here). Failure mode is logged, narrow.

**Low — `org.created` (and other non-audit rows) are pruned at 24 months** although "audit events survive until hard delete"; the org's creation record disappears. Decision whether `org.created` should be audit-class.

**Low — Doc drift.** CLAUDE.md says `contacts.artist_org_id` is RESTRICT; migration 154 is `ON DELETE SET NULL` (behaviour verified; SET NULL is correct for purge). `isLabelOsRestoreApiPath` regex is lower-case-only (an upper-case id URL falls to the member gate).

### 5. Decisions for the product owner
1. **Who may list on the producer's store (exact mechanics).** Eligible: releases of the store owner's personal `producer` org, plus any **artist org with an *active* connection to a `label` org the store owner owns** (`loadStoreOwnerOrgs`). Any member of that artist org with `release.write` (owner/admin/member functions per 06 §) can list a *released* release of that org in `preview` mode via `PUT /api/org/<artist>/releases/<id>/store`; `full` needs owner/admin of the artist org. **The store owner is not asked and has no per-release surface**: no route, page or event on their side lists, previews or unlists another org's release (only `api/org` routes of the listing org touch `releases`). Their controls are all-or-nothing: end the connection, or delete the label org → artist releases drop from the store within ~30 s + CDN. Recommendation: keep the model (accepting the connection is the consent) but add a store-owner "Releases from connected artists" list with an Unlist/veto button, and say so on the connection-accept screen.
2. **Full playback vs "going out / is out".** Code: playback is a static per-release choice (`preview` default, `full` owner/admin). A release can only be on the store once *released* (imported, or delivered with `release_date` ≤ today UTC), re-checked on every request; there is no "going out" state (a delivered release dated next month cannot be listed at all, so no pre-release teaser). Unlisting resets playback to `preview`. Not tied to anything else: an owner/admin may pick `full` for any released listing, and an owner/admin can import any release as "already released". Recommendation: default `full` only when the release date has come and only as a derived lossy full-length stream (not the stored master), behind a durable per-IP limiter; keep `preview` for anything else.
3. Add a time budget to the purge cron? (recommend yes.) Make `org.created` audit-class? (recommend yes.)
